# token-meter

Фактические токены и скорость ответов ассистента в BB. Плагин не оценивает usage и не подставляет числа: если BB не сообщил usage для хода, интерфейс остаётся пустым.

## Что показывается

У последнего смонтированного assistant-сообщения хода в `actionRow` появляется бейдж:

```text
↑1.2k ↓740 · cache 265k · 59.2 ток/с
```

- `↑` — `inputTokens` последнего usage-снимка хода;
- `↓` — `outputTokens`;
- `cache` — `cachedInputTokens`;
- `ток/с` — output, делённый на wall-clock время от `turn/started` до `turn/completed`; значение округляется до 0.1. Оно отображается только при длительности ≥1 секунды и `outputTokens > 0`. Это не отдельная метрика провайдера.
- В `title` бейджа — полные числа: вход, cache read/write, выход, reasoning, total хода и длительность.

Один бейдж на ход выбирается по максимальному `message.createdAt` среди realized-сообщений, для которых BB смонтировал metadata-slot: у metadata-slot нет доступа к соседним сообщениям хода, поэтому плагин ведёт общий на вкладку реестр смонтированных сообщений по `threadId:turnId`. Если BB виртуализирует список, выбор действует внутри смонтированного набора; дополнительный запрос всей timeline ради этого не выполняется.

В строке контекста треда показывается сводка:

```text
Σ 531k токенов · ~40 ток/с
```

`Σ` — последний cumulative `tokenUsage.total.totalTokens` от провайдера, а не сумма вычисленная плагином. Средняя скорость считается только по сохранённым ходам, у которых есть `tokPerSec`.

## Почему бейджа может не быть

- Usage отдают только провайдеры **pi** и **codex**. Для **command-code** и **gemini-web** BB не создаёт такие данные.
- BB не хранит полную историю usage: в event log треда обычно остаётся одно (реже два) последних события `thread/tokenUsage/updated`, новые вытесняют старые. Поэтому полной истории до установки плагина восстановить нельзя. Плагин копит свою per-turn историю с момента установки; при первом сигнале он может сохранить последний ещё доступный BB снимок, но не вытесненные.
- Для сообщений вне хода (`turnId === null`), user-сообщений, неполных/невалидных usage и ходов без сохранённой записи ничего не рисуется.

## Откуда берутся данные

Сервер плагина подписан на `experimental_thread.events` (debounce ≤1/с на тред). На каждом сигнале он дочитывает `bb.sdk.threads.events.list({ threadId, afterSeq, types: ["thread/tokenUsage/updated", "turn/started", "turn/completed"], order: "asc" })` от сохранённой позиции. `turnId` события берётся из его turn-скоупа (`scope.turnId`); отдельного поля `turnId` в строке события нет.

## Хранение и ограничения

Данные живут в `bb.storage.kv` в bb.db:

- `token-meter:turn:<threadId>:<turnId>` — последний usage хода, дедупликация по `turnId`;
- `token-meter:thread:<threadId>` — сводка;
- `token-meter:seq:<threadId>` — последовательность, с которой продолжается catch-up.

На тред сохраняются не более **500** новых ходов. При запуске плагина записи старше **30 дней** удаляются. Начало хода (`turn/started`) ищется в пределах 20 событий перед usage-событием; если оно недоступно, `durationMs = null`, а скорость не показывается. Если в одном ходе встретилось несколько usage-событий, побеждает последнее по sequence.

Realtime-канал `token-meter-changed` обновляет keyed RPC `turn_usage` и сводку `thread_usage`. В RPC отсутствующая запись возвращается как `null`; optional-поля не уходят в JSON как `undefined`.
