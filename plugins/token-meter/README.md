# token-meter

Фактические токены и скорость ответов ассистента в BB. Плагин не оценивает usage и не подставляет числа: если BB не сообщил usage для хода, интерфейс остаётся пустым.

## Что показывается

У последнего смонтированного assistant-сообщения хода в `actionRow` появляется бейдж:

```text
↑1.2k ↓740 · cache 265k · 59.2 ток/с
```

- `↑` — `inputTokens` последнего usage-снимка;
- `↓` — `outputTokens`;
- `cache` — `cachedInputTokens`;
- `ток/с` — `outputTokens` последнего **вызова модели**, делённые на wall-clock время этого вызова. Окно вызова — от завершения последнего инструмента хода (`item/completed` с видом не `agentMessage`/`reasoning`) до `turn/completed`; если инструментов в ходе не было — от `turn/started`. Значение округляется до 0.1 и показывается только при окне ≥1 секунды и `outputTokens > 0`. Это не provider-native tokens/sec.
- В `title` бейджа — полные числа: вход, cache read/write, выход, reasoning, total вызова, длительность последнего вызова модели и отдельно длительность всего хода.

Один бейдж на ход выбирается по максимальному `message.createdAt` среди realized-сообщений, для которых BB смонтировал metadata-slot: у metadata-slot нет доступа к соседним сообщениям хода, поэтому плагин ведёт общий на вкладку реестр смонтированных сообщений по `threadId:turnId`. Если BB виртуализирует список, выбор действует внутри смонтированного набора; дополнительный запрос всей timeline ради этого не выполняется.

Практические следствия: в `actionRow` бейдж показывается вместе с остальными действиями, то есть у старых ответов виден на hover; сообщения в свёрнутых группах timeline не монтируются, поэтому бейджа у них нет, пока группа не раскрыта.

В строке контекста треда показывается сводка:

```text
Σ 531k токенов · ~40 ток/с
```

`Σ` — сумма `total` последних вызовов модели по записанным ходам. Это сумма плагина, а не cumulative `total` провайдера: pi держит свой total в памяти хоста и сбрасывает его при рестарте, поэтому провайдерский счётчик «прыгает» назад. У pi сумма плагина совпадает с его cumulative; у codex она может быть меньше реальной — эмпирически не проверено. Средняя скорость считается только по сохранённым ходам, у которых есть `tokPerSec`.

## Почему бейджа может не быть

- Usage отдают только провайдеры **pi** и **codex**. Для **command-code** и **gemini-web** BB не создаёт такие данные.
- BB не хранит полную историю usage: в event log треда обычно остаётся одно (реже два) последних события `thread/tokenUsage/updated`, новые вытесняют старые. Поэтому полной истории до установки плагина восстановить нельзя. Плагин копит свою per-turn историю с момента установки; при первом сигнале он может сохранить последний ещё доступный BB снимок, но не вытесненные. Если плагин выгружен дольше, чем bb хранит события треда (его собственное окно prune), usage-события этих ходов теряются окончательно.
- Для сообщений вне хода (`turnId === null`), user-сообщений, неполных/невалидных usage и ходов без сохранённой записи ничего не рисуется.

## Откуда берутся данные

Сервер плагина подписан на `experimental_thread.events` (debounce ≤1/с на тред). На каждом сигнале он дочитывает `bb.sdk.threads.events.list({ threadId, afterSeq, types: ["thread/tokenUsage/updated", "turn/started", "turn/completed"], order: "asc", limit: "100" })` от сохранённой позиции — страницами по 100, потому что bb отвечает HTTP 400 на больший `limit`. `turnId` события берётся из его turn-скоупа (`scope.turnId`); отдельного поля `turnId` в строке события нет.

Границы окна последнего вызова модели уточняются вторым запросом: `types: ["item/started", "item/completed"], beforeSeq: <seq usage-события>, order: "desc", limit: "10"` — берётся последний `item/completed` этого хода, вид которого не `agentMessage` и не `reasoning`. Если на странице инструмента не нашлось и ход ещё не кончился, окно считается неизвестным: `durationMs` и `ток/с` не записываются (лучше пусто, чем окно=весь ход).

## Хранение и ограничения

Данные живут в `bb.storage.kv` в bb.db:

- `token-meter:turn:<threadId>:<turnId>` — последний usage хода, дедупликация по `turnId`;
- `token-meter:thread:<threadId>` — сводка;
- `token-meter:seq:<threadId>` — последовательность, с которой продолжается catch-up.

На тред сохраняются не более **500** новых ходов. При запуске плагина записи старше **30 дней** удаляются. Начало хода (`turn/started`) ищется в пределах 20 событий перед usage-событием; если оно недоступно, `durationMs = null`, а скорость не показывается. Если в одном ходе встретилось несколько usage-событий, побеждает последнее по sequence.

Обновление интерфейса идёт через теги RPC-кэша: `turn_usage` объявляет `keyTags` → `thread:<threadId>`, `thread_usage` — `tags` → `thread:<threadId>`, а сервер после записи и после `thread.deleted` вызывает `bb.rpc.experimental_invalidate(["thread:<threadId>"])`. Никаких realtime-подписчиков на каждый бейдж нет: один сигнал обновляет все запросы этого треда.

Удаление треда (`thread.deleted`) стирает все его ключи. Startup-prune удаляет ходы старше 30 дней и оставшиеся без ходов сводки и позиции `afterSeq`.

В RPC отсутствующая запись возвращается как `null`; optional-поля не уходят в JSON как `undefined`.
