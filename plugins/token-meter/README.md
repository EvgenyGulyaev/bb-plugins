# token-meter

Фактические токены и скорость ответов ассистента в BB. Плагин не оценивает usage и не подставляет числа: если BB не сообщил usage для хода, интерфейс остаётся пустым.

## Что показывается

У последнего смонтированного assistant-сообщения хода в `actionRow` появляется бейдж:

```text
↑1.2k ↓740 · cache 265k · 59.2 ток/с (эфф.) · модель ~207
```

- `↑` — `inputTokens` последнего usage-снимка;
- `↓` — `outputTokens`;
- `cache` — `cachedInputTokens`;
- `ток/с (эфф.)` — **эффективная** скорость: `outputTokens` последнего **вызова модели**, делённые на wall-clock время этого вызова. Окно — от завершения последнего инструмента хода (`item/completed` с видом не `agentMessage`/`reasoning`) до `turn/completed`; если инструментов в ходе не было — от `turn/started`. Значение показывается только при окне ≥1 секунды и `outputTokens > 0`: целым при ≥100 ток/с, с одним знаком после запятой при меньшей скорости. Это не provider-native tokens/sec.
- `модель ~207` — округлённый результат последнего прямого замера чистой генерации для модели этого хода; отображается только после ручного замера.
- В `title` бейджа — полные числа: вход, cache read/write, выход, reasoning, total вызова; `Последний вызов: N с · Весь ход: M с`; объяснение эффективной скорости. Она включает ожидание первого токена: обработку контекста, очередь и скрытое рассуждение. Если замер модели есть, там же `Чистая генерация модели …`, задержка и дата замера.

Один бейдж на ход выбирается по максимальному `message.createdAt` среди realized-сообщений, для которых BB смонтировал metadata-slot: у metadata-slot нет доступа к соседним сообщениям хода, поэтому плагин ведёт общий на вкладку реестр смонтированных сообщений по `threadId:turnId`. Если BB виртуализирует список, выбор действует внутри смонтированного набора; дополнительный запрос всей timeline ради этого не выполняется.

Практические следствия: в `actionRow` бейдж показывается вместе с остальными действиями, то есть у старых ответов виден на hover; сообщения в свёрнутых группах timeline не монтируются, поэтому бейджа у них нет, пока группа не раскрыта.

В строке контекста треда показывается сводка:

```text
Σ 531k токенов · ~40 ток/с (эфф.)
```

`Σ` — сумма `total` последних вызовов модели по записанным ходам. Это сумма плагина, а не cumulative `total` провайдера: pi держит свой total в памяти хоста и сбрасывает его при рестарте, поэтому провайдерский счётчик «прыгает» назад. У pi сумма плагина совпадает с его cumulative; у codex она может быть меньше реальной — эмпирически не проверено. Средняя скорость считается только по сохранённым ходам, у которых есть `tokPerSec`.

## Эффективная и чистая скорость — не одно и то же

Прежняя идея считать «чистую генерацию» как `outputTokens / (item/started agentMessage → item/completed)` **неверна**. Pi отдаёт сообщение bb целиком или крупными кусками: прямой стрим через relay при проверке пришёл одним куском за 1–4 мс. Поэтому окно сообщения измеряет задержку доставки события в bb, а не печать токенов моделью. События bb не позволяют отделить ожидание первого токена от генерации.

Поэтому плагин разделяет метрики:

1. **Эффективная скорость последнего вызова** — `output / окно последнего вызова`. Она честно показывает пользовательское wall-clock время и включает prefill, очередь, скрытое рассуждение и ожидание первого токена.
2. **Чистая скорость генерации** — только прямой замер выбранной модели по кнопке. События bb для неё не используются.

### Как включить прямой замер

По умолчанию `benchEnabled = false`: плагин не отправляет никаких запросов. В **Settings → Installed plugins → Token meter** задайте:

- `benchEndpoint` — OpenAI-совместимый base URL, например `http://localhost:8317/v1` (для документации внешний адрес обозначается только как `https://example.com/v1`); логин/пароль в URL не поддерживаются;
- `benchApiKey` — необязательный ключ, secret-настройка; он не возвращается через RPC, не попадает в UI и не логируется;
- `benchEnabled` — включить ручной замер.

В секции **«Замер скорости модели»** (`app.slots.settingsSection`) перечислены уникальные `model` из сохранённых ходов. У каждой виден последний замер (дата — в локальном времени) и кнопка **«Замерить»**. При выключенной или неполной конфигурации показывается подсказка, а кнопка неактивна.

**Цена замера:** один замер — это **4 платных запроса** к вашей модели, до **~3300 выходных токенов** суммарно и до **~8 минут** в худшем случае (таймаут 120 с на каждый запрос, то есть четыре таймаута подряд). Запросы уходят только по нажатию кнопки.

Один замер делает четыре последовательных non-stream `POST {benchEndpoint}/chat/completions` с одним промптом и `max_tokens` в порядке **150, 1500, 150, 1500**. По `usage.completion_tokens` и wall-clock времени двух пар считаются средние, затем:

```text
rate = (avgOut1500 − avgOut150) / ((avgMs1500 − avgMs150) / 1000)
latency = avgMs150 − avgOut150 / rate * 1000
```

Таймаут запроса — **120 секунд**, в том числе на чтении тела ответа (тогда сообщение говорит про таймаут, а не про «не JSON»). Отмена запроса клиентом прерывает HTTP и освобождает single-flight. Endpoint с логином/паролем в URL отклоняется: такой адрес утёк бы в тексты ошибок. Одновременно разрешён один замер. Неположительный или нечисловой `rate` отклоняется как «замер неустойчив»; HTTP, сетевые и usage-ошибки показываются понятным сообщением. Результат не выдумывается и не заменяется эффективной скоростью. Проверочный ориентир описанной методики: `deepseek-v4.1-flash ≈207 ток/с` и около `1 с` фиксированной задержки; это пример измерения, а не встроенная константа.

## Почему бейджа может не быть

- Usage отдают только провайдеры **pi** и **codex**. Для **command-code** и **gemini-web** BB не создаёт такие данные.
- BB не хранит полную историю usage: в event log треда обычно остаётся одно (реже два) последних события `thread/tokenUsage/updated`, новые вытесняют старые. Поэтому полной истории до установки плагина восстановить нельзя. Плагин копит свою per-turn историю с момента установки; при первом сигнале он может сохранить последний ещё доступный BB снимок, но не вытесненные. Если плагин выгружен дольше, чем bb хранит события треда (его собственное окно prune), usage-события этих ходов теряются окончательно.
- Для сообщений вне хода (`turnId === null`), user-сообщений, неполных/невалидных usage и ходов без сохранённой записи ничего не рисуется.

## Откуда берутся данные

Сервер плагина подписан на `experimental_thread.events` (debounce ≤1/с на тред). На каждом сигнале он дочитывает `bb.sdk.threads.events.list({ threadId, afterSeq, types: ["thread/tokenUsage/updated", "turn/started", "turn/completed", "client/turn/requested"], order: "asc", limit: "100" })` от сохранённой позиции — страницами по 100, потому что bb отвечает HTTP 400 на больший `limit`. `turnId` события берётся из его turn-скоупа (`scope.turnId`); отдельного поля `turnId` в строке события нет.

Модель хода берётся из события, а не из дефолта треда: `model` = `data.execution.model` последнего `client/turn/requested` перед `turn/started` этого хода (третий запрос — `types: ["client/turn/requested"], beforeSeq: <seq usage>, order: "desc", limit: "20"`). Это единственный точный источник: дефолт треда — это модель на момент синка, поэтому при catch-up бэклога и при смене модели между ходами он дал бы всем ходам одну и ту же (текущую) модель. Кэша модели нет: у каждого хода своё событие. `bb.sdk.threads.defaultExecutionOptions({ threadId })` вызывается только как fallback, когда `client/turn/requested` не нашёлся (старые события вне окна bb, спавн).

`providerId` — свойство треда, а не хода, и есть только в `bb.sdk.threads.get({ threadId })` (`ThreadResponse.providerId`); `defaultExecutionOptions` его не отдаёт. Один запрос на тред кэшируется на **60 секунд**. Ошибка любого из этих вызовов не мешает сохранить usage, а отсутствующие поля не записываются как `undefined`.

Границы окна последнего вызова модели уточняются вторым запросом: `types: ["item/started", "item/completed"], beforeSeq: <seq usage-события>, order: "desc", limit: "10"` — берётся последний `item/completed` этого хода, вид которого не `agentMessage` и не `reasoning`. Если на странице инструмента не нашлось и ход ещё не кончился, окно считается неизвестным: `durationMs` и `ток/с` не записываются (лучше пусто, чем окно=весь ход).

## Хранение и ограничения

Данные живут в `bb.storage.kv` в bb.db:

- `token-meter:turn:<threadId>:<turnId>` — последний usage хода, дедупликация по `turnId`;
- `token-meter:thread:<threadId>` — сводка;
- `token-meter:seq:<threadId>` — последовательность, с которой продолжается catch-up;
- `token-meter:bench:<model>` — последний прямой замер `{ model, genTokPerSec, latencyMs, at, samples }`.

На тред сохраняются не более **500** новых ходов. При запуске плагина записи старше **30 дней** удаляются. Начало хода (`turn/started`) ищется в пределах 20 событий перед usage-событием; если оно недоступно, `durationMs = null`, а скорость не показывается. Если в одном ходе встретилось несколько usage-событий, побеждает последнее по sequence.

Обновление интерфейса идёт через теги RPC-кэша: `turn_usage` объявляет `keyTags` → `thread:<threadId>`, `thread_usage` — `tags` → `thread:<threadId>`, а сервер после записи и после `thread.deleted` вызывает `bb.rpc.experimental_invalidate(["thread:<threadId>"])`. `bench_results` (замеры для бейджа) и `bench_list` (замеры + модели + состояние настроек для секции настроек) используют тег `bench`, который инвалидируется после замера и смены настроек. Бейдж намеренно не зовёт `bench_list`: ему нужны только готовые замеры. Никаких realtime-подписчиков на каждый бейдж нет: один сигнал обновляет все запросы этого треда.

Удаление треда (`thread.deleted`) стирает все его ключи. Startup-prune удаляет ходы старше 30 дней и оставшиеся без ходов сводки и позиции `afterSeq`.

В RPC отсутствующая запись возвращается как `null`; optional-поля не уходят в JSON как `undefined`.
