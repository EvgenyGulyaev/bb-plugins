# Api модели (clirelay-test)

BB-плагин для лёгкого подключения моделей с API-адресов в [pi](https://pi.dev).
Источник истины — `~/.pi/agent/models.json`; pi подхватывает изменения при открытии `/model`.

## Раскладка

Иконка «Api модели» в левом рейле → панель с двумя вкладками:

- **«Аккаунты»** (дефолт) — карточки квот аккаунтов relay, как в manage-UI clirelay:
  в шапке почта аккаунта (из `auth-files`), хэш `auth_index` — мелким ниже и в тултипе;
  без почты — хэш. Бейджи (план, провайдер, Cycle, Success Rate, restriction),
  строки квот с баром остатка (`percent`), countdown до сброса (`reset_at`) и потраченной
  суммой из `used_cost_usd` (только при значении >0). Если `reset_at` отсутствует, но есть
  `window_seconds`, карточка различает «окно не начато» (100%) и «сброс неизвестен»;
  Claude 5 ч при полном остатке не отдаёт `reset_at`, потому что окно ещё не начато.
  Из `usage` добавляется чип `$… за 7 дн` (`cost_total_7d`); его title содержит `cost_total`,
  `cycle_cost_total` и `request_total_7d`, а при `cycle_known:false` цикл помечен неизвестным.
  Деньги форматируются через `lib/money.ts`: центы с двумя знаками, суммы ≥$1000 — в `k`.
  лейблы квот на русском (словарь известных + разбор ключей вида `m_quota.code_5h`
  → «Код · 5 ч», исходный ключ — в тултипе); Success Rate нормализуется из доли 0..1;
  бар зелёный при остатке >20%, красный ≤20%. Карточки компактные, не растягиваются по высоте строки.
  Верхний уровень — аккордеоны «С квотой» (открыт) и «Без квот» (свёрнут, тонкие строки).
  Внутри — под-аккордеоны провайдеров только когда оба фильтра «Все» или аккаунтов > 20,
  иначе плоская сетка; сортировка: с квотой первыми, выключенные после включённых.
  Фильтры «Все/Вкл/Выкл» (дефолт «Вкл») и по провайдеру. Бейджи ok/active/disabled скрыты,
  когда рядом есть тумблер (не дублируют состояние).
  Тумблер вкл/выкл аккаунта (`PATCH /v0/management/auth-files/status`) — только у своих
  аккаунтов (есть запись в auth-files); у shared-аккаунтов тумблера нет, их `disabled`
  берётся из `health_status`. Обновление кнопкой ⟳ на группу. Данные: management API clirelay
  `GET {origin}/v0/management/ai-accounts/status` (нужны логин/пароль админки relay, см. ниже).
  Без кредов — бейдж «креды не заданы» в шапке группы и кнопка «Креды» (диалог per-URL);
  при ошибке ключа — понятный текст.
  **Кольца квот в рейле:** на каждой карточке — галочка «Кольцо в рейле»;
  отмеченные аккаунты показываются кольцами в левом рейле под кнопкой настроек
  (кольцо + логотип провайдера внутри + процент остатка снизу). В тулбаре вкладки —
  ползунок «Размер колец» (24–64px, шаг 2) и поле «В строке» (1–4 колонки).
  **Одно кольцо на тип провайдера** (kimi, claude, grok, gpt, иначе id провайдера):
  если отмечено два и более аккаунта одного типа, кольцо показывает **больший
  остаток среди активных** («больший активный из N» в подсказке), выключенные
  аккаунты в максимум не входят; если активных нет — «—» и пунктирное кольцо.
  Процент — остаток первой квоты с `percent`; клик по кольцу открывает список
  всех отмеченных аккаунтов типа (активные первыми, затем по убыванию остатка,
  выключенные помечены) с их квотами, русскими лейблами, стоимостью и countdown до сброса
  (либо тем же fallback «окно не начато»/«сброс неизвестен»); у аккаунта видна сумма за 7 дн.
  Цвет кольца: обычный, предупреждающий (≤20%), критический (≤5%).
  Данные колец — тот же RPC `relay_accounts` (плюс `providers_list`), опрос раз в минуту
  при видимой вкладке и обновление по realtime; нового серверного похода за квотами нет.
  Выбор аккаунтов и размеры хранятся в kv `relay-rings`
  (`{ selected: string[], size: number, perRow: number }`, ключ аккаунта `${origin}|${auth_index}`).
- **«Подключение»** — управление моделями pi:

```
[＋ Добавить API]
▼ my-router         …:8080/v1   3 подкл.   [⟳] [⚙] [✕]
  ┌ Доступные (GET /models) ─┐ ┌ Подключённые (в pi) ─────────┐
  │ model-large        [＋]  │ │ ▶ model-flash                │
  │ model-new          [＋]  │ │ ▼ model-pro            [✕]   │
  │ (подключённые скрыты)    │ │   reasoning      [✓] bool    │
  └──────────────────────────┘ │   contextWindow  [400000] int│
                               │   maxTokens      [64000] int │
                               │   input          [text|image]│
                               │   [Тест] [Сохранить]         │
                               └──────────────────────────────┘
▶ other-api       …
```

- Аккордеон верхнего уровня — API-адрес (провайдер `models.json`).
  Если несколько провайдеров сидят на одном адресе — они показываются вложенно
  под общей группой адреса (аккордеон адреса → аккордеоны провайдеров).
- Слева — новые модели с `GET {baseUrl}/models` (нет ни в подключённых, ни в выключенных);
  «＋» подключает обычным путём, кнопка с настройками донора клонирует их (см. «Синхронизация»).
  Если эндпоинт не отдаёт `/models` — ошибка + ручное добавление по id;
  автоповтора после ошибки нет (иначе недоступный эндпоинт крутил цикл ретраев), повтор — ⟳.
- Обе колонки сгруппированы по семейству модели (Claude/GPT/Gemini/Qwen/Kimi/
  DeepSeek/Grok/Llama/Mistral/Другие — по префиксу id).
- Справа — подключённые и выключенные модели; тумблер вкл/выкл у каждой строки:
  выключенная запись переезжает в хранилище плагина с сохранением настроек,
  pi видит только включённые; фильтр «Все / Вкл / Выкл» со счётчиками.
  Аккордеон модели → форма настроек.
  Кнопка «Тест» шлёт минимальный реальный запрос (`POST /chat/completions`,
  `max_tokens: 8`, таймаут 30с) и показывает латентность и кусочек ответа;
  ошибки санитизируются. v1: только `openai-completions`.
- Форма генерится из схемы полей (`lib/schema.ts`): bool → чекбокс, int → число,
  enum → селект, multiselect → чекбоксы, JSON-поля → textarea с zod-валидацией.
  Базовые: `name`, `reasoning`, `contextWindow`, `maxTokens`, `input`.
  Секция «API-настройки» (сворачиваемая): `api`/`baseUrl` (переопределения
  провайдера), `apiKey` модели, `headers`, `thinkingLevelMap`, `samplingParams`,
  `samplingParamsByThinkingLevel`, `compat`, `cost`, `promptCache`, `inputLimits`.

## Сценарий

1. «Добавить API» → id (slug), имя, baseUrl, тип API, ключ.
2. Раскрыть адрес → список доступных загрузится сам.
3. «＋ Подключить» → модель появилась справа и в `models.json`. Для апгрейда версии —
   кнопка «Подключить с настройками <донор>» и подтверждение в диалоге.
4. Раскрыть модель → настроить → «Сохранить».
5. В pi открыть `/model` — модель доступна.

## Установка

```bash
npm install
bb plugin build
bb plugin install .
```

Тесты: `npm test` (vitest). Типы: `npm run typecheck`.

## Конфигурация

Путь к файлу pi настраивается (дефолт `~/.pi/agent/models.json`):

```bash
bb plugin config clirelay-test set modelsPath /path/to/models.json
bb plugin reload clirelay-test   # настройка читается при загрузке
```

То же поле — в Settings → Installed plugins → Api модели.
`PI_MODELS_PATH` — тестовый шов, имеет приоритет над настройкой.

Логин и пароль админки relay (для вкладки «Аккаунты») задаются **per-URL**: кнопка
«Креды» у каждой группы адреса открывает диалог (логин/пароль, сохранить/очистить).
Креды хранятся в server-side kv плагина по origin (`relay-creds:<origin>`), сессии —
там же (`relay-auth:<origin>`); плагин сам логинится (`POST {origin}/v0/auth/login`)
и продлевает сессию через `/v0/auth/refresh`. Глобальные secret-настройки
`managementUser` / `managementPassword` (файл 0600, не попадают в db/фронтенд/репо) —
fallback для адресов без своих кредов:

```bash
bb plugin config clirelay-test set managementUser <логин админки>
bb plugin config clirelay-test set managementPassword <пароль админки>
bb plugin reload clirelay-test
```

Если у адреса нет management API (например, другой сервис вместо clirelay) —
группа покажет ошибку HTTP, остальные адреса работают независимо.

## Логотипы провайдеров

Кольца рисуют логотип внутри кольца. Для kimi/moonshot, claude/anthropic,
grok/xai и gpt/openai/chatgpt вендорены SVG из
[lobehub/lobe-icons](https://github.com/lobehub/lobe-icons) (MIT) — файлы лежат в
`assets/`, константы — в `lib/provider-logos.ts` (см. `assets/README.md`).
Неизвестный провайдер показывается первой буквой имени. HTML вставляется
только из этих констант; данные relay в разметку не попадают.

## Секретность

Ключи и адреса живут только в `~/.pi/agent/models.json` (вне репо), креды админки —
в secret-настройках плагина, сессии — в server-side kv. В коде, тестах и доках —
только выдуманные `localhost`.
`apiKey` и `headers` никогда не возвращаются фронтенду; ошибки discovery и
management API санитизируются (без URL). Синхронизатор моделей держит клон донора
только на сервере: `models_sync_scan` отдаёт лишь `id`/`name`/`enabled` донора и его
несекретные лимиты/`input`, `model_sync_apply` возвращает только статус и источники
полей.
Запись файла атомарная (tmp + rename) с ротацией `.bak`; неизвестные поля сохраняются.

## Ограничения v1

- Таргет — только pi.
- Кольца только для аккаунтов, у которых relay отдаёт квоты: без `percent`
  кольцо рисуется пунктиром с «—», попавер показывает, что квоты нет.
- Кольца появляются в рейле, пока вкладка bb видима; данные обновляются раз в
  минуту (и по realtime). В качестве источника — существующий `relay_accounts`,
  поэтому нужны те же креды админки relay.
- Якорь колец вставлен в разметку рейла bb; при смене этой разметки кольца
  просто не появятся (панель продолжает работать).
- Ключи `!command` не резолвятся для discovery (literal и `$ENV` — да).

## Синхронизация новых моделей

Слева в «Подключении» показываются только **новые** для провайдера модели:
id из `GET /models`, которого нет ни в `models`, ни в `disabled`. Кнопка
**«Проверить обновления»** (и автозагрузка при раскрытии адреса) вызывает
`models_sync_scan`: сетевой запрос, никаких записей. После ошибки автоповтора нет —
повтор только кнопкой.

Из ответа API читается только whitelist: `context_window`/`max_context_window`,
`max_output_tokens`/`max_tokens`, `input_modalities`, `supported_reasoning_levels`.
`pricing`, `description` и прочие поля игнорируются; строки/float/0/отрицательные
числа и значения сверх границ (context ≤ 10 000 000, maxTokens ≤ 1 000 000) не
принимаются, конфликт alias-пары → поле считается ненадёжным и берётся fallback.

Донор подбирается детерминированно (`lib/model-sync.ts`, без LLM и fuzzy): тот же
provider, точно равные `(family, variant)` из парсинга id, и только более старая
версия. Один максимум версии → кнопка **«Подключить с настройками <донор>»**;
равный максимум версии у разных id → только ручной select «Скопировать настройки
из…» с кандидатами; дубликат id в pool → донора нет и кандидатов нет (даже если
версия старше новой); нет пары, уже есть версия ≥ новей, downgrade или
непарсящийся id → обычное «Подключить».

Три вида строк:

| Вид | Что видно |
|---|---|
| Обновление версии | бейдж «Обновление», донор, источники лимитов, кнопка с настройками донора |
| Новая, донор неоднозначен | select без выбора, «С настройками…» заблокирована до выбора |
| Просто новая | только «Подключить» (старый `model_connect`) |

Подтверждение — общий диалог: новый id, донор, категории переносимых настроек
(API/baseUrl, reasoning, input, sampling, compat, cost/promptCache, ключ и заголовки
donor — **без значений секретов**), итоговые `contextWindow`/`maxTokens`/`input` с
пометкой источника (`API`, `donor fallback`, `pi default`) и галочка **«Заменить в
выборе pi»** (по умолчанию снята). До нажатия «Подключить» записей нет.

`model_sync_apply {providerId, modelId, donorId, replaceInPi}`:

- повторно читает `GET /models` и клонирует донора **на сервере** (apiKey и значения
  headers не покидают сервер); new model исчезла из API и не подключена → ошибка без записи;
- пишет `models.json` атомарно и публикует `api-models-changed`; старая модель не
  отключается и не удаляется, `defaultModel`/`defaultProvider`/pi/треды не меняются;
- `replaceInPi:false` (галочка снята) → `settings.json` не читается и не пишется;
- `replaceInPi:true` → preflight `settings.json` **до** записи models: битый JSON,
  не-object root, не тот тип `enabledModels`/`compaction`/`compaction.modelOverrides` →
  ошибка, оба файла байт-в-байт; из `modelOverrides` проверяются только donor/new
  ключи — посторонняя битая запись sync не блокирует;
- если models записан, а запись settings упала → `status:"partial"`, `settings:"failed"`;
  UI показывает «Модель подключена, выбор pi не изменён. Повторите с той же галочкой»,
  повтор не переклонирует модель и добирает только недостающий settings patch;
- полный успех → `status:"applied"`, отсутствие изменений → `noop`. Ответ содержит
  `modelAdded` и `sources` (обязателен при `modelAdded:true`). Повтор без галочки —
  `noop`, повтор с галочкой, который действительно дописал settings — `applied`
  (`modelAdded:false, settings:"updated"`);
- донор валидируется на сервере в обеих ветках (added и retry): допускается только
  автодонор или кандидат из tie, `modelId` в retry обязан быть подключён
  (`hasModel`), выключенная модель → ошибка без записи;

`settings.json` берётся рядом с `models.json` (`join(dirname(modelsPath), "settings.json")`),
отдельной настройки нет. Патчатся только exact-ключи `${providerId}/${modelId}`:

- `enabledModels`: отсутствует → не создаётся (создание одного pattern ограничило бы
  остальные модели); array → exact donor заменяется на new на позиции первого donor,
  лишние exact donor/new убираются, wildcards и partial patterns не трогаются;
  exact donor нет → `enabledModels` байт-в-байт (new и его дубли остаются как есть);
- `compaction.modelOverrides[donorKey]` при отсутствии `newKey` — deep clone на new key,
  donor override сохраняется; new уже есть — не перезаписывается;
- `defaultModel`, `defaultProvider`, `modelThinkingLevels`, project settings и прочие
  ключи не меняются; `settings:"unchanged"` — допустимый успех.

После подключения UI пишет toast «Подключена …; открой /model в pi заново». Никакого
restart/refresh pi плагин не делает.

## API-настройки моделей и провайдеров

Секция «API-настройки» в форме модели (вкладка «Подключение» → аккордеон модели):

- `api` / `baseUrl` — переопределения провайдера; пусто = наследовать.
- `thinkingLevelMap` — какие значения pi шлёт провайдеру для уровней
  `off/minimal/low/medium/high/xhigh/max`; `null` = уровень недоступен.
- `samplingParams` / `samplingParamsByThinkingLevel` — поля тела запроса
  (например `reasoning_effort`) и переопределения по уровням thinking;
  только OpenAI-compatible API.
- `compat` — совместимость с API (`supportsDeveloperRole`, `supportsStore`,
  `promptCacheKeyMode`, `thinkingFormat`, …). Подсказка под полем перечисляет
  документированные поля для текущего api; неизвестные поля сохраняются как есть.
- `cost` — USD за 1M токенов (`input/output/cacheRead/cacheWrite` обязательны,
  `tiers` — пороги по входу запроса), `promptCache` — секунды жизни кэша
  `{short, long}`, `inputLimits` — лимиты размера запроса и изображений.
- JSON-поля редактируются текстом с валидацией: ошибка показывает поле и путь.
  Пустое поле = удалить настройку из models.json.

Секреты: `apiKey` модели и значения `headers` никогда не возвращаются фронтенду —
видны только флаг «задан» и имена заголовков. Ключ: пусто = не менять, кнопка
«Очистить» = удалить. Заголовки: ввод мержится по ключам на сервере
(`""`-значение удаляет ключ, «Очистить все» удаляет поле), невидимые значения
сохраняются. Запись атомарная, неизвестные поля файла не теряются.

В форме провайдера («Настроить адрес»): `authHeader` (Authorization: Bearer),
`oauth` (radius), `compat` и `headers` провайдера — с той же секретной семантикой.
`modelOverrides` не редактируется и сохраняется в файле как есть.
